# 票 93 — 本地开发环境一条命令起全套（系统提升 B4，修复收官后开工）

严重度：S3（效率与可复现性，但已实际造成损失）
来源：Forrest 补充任务单 B 组 B4（2026-10-23）

## 事实
- 当前起环境靠**手工脚本 + 经验**（本沙盒内我起的这一套就是逐个服务手工 `dotnet run`，外加手工建库、手工跑 7 个服务迁移、手工起 RabbitMQ、手工起 Angular dev server）。
- 已在"页面能开但 API 全 500"这类问题上**栽过多次**——根因就是起服务与起数据库/迁移的先后顺序、依赖等待没有自动化保障。

## 任务
1. 把 `docker compose` 做成**一条命令**（如 `docker compose up` / `./scripts/dev-up.sh`）全起：PostgreSQL + RabbitMQ + 7 个微服务 + 网关 + Angular。
2. **依赖等待**：服务起来不等于可用——必须等数据库可连接、等 RabbitMQ 就绪、等迁移跑完，再对外宣告就绪。用 healthcheck + depends_on condition 或显式 wait 脚本，不许靠 sleep 猜。
3. **起后自检报告**：跑完输出一份自检结果，哪个服务没活、哪个端点不通**一眼可见**（不要让人去翻日志猜）。
4. **README 写清前置条件**：Docker 必须开着、端口占用、需要的凭据（AI/OCR/TTS 等）、首次要跑迁移这类坑全部写明。

## 验收
- 干净机器上一条命令跑完，自检报告全绿（或明确指出哪一项没起来、为什么）。
- 反向验证：故意停掉其中一个依赖（如 Postgres 没起），一条命令必须**明确报出哪一项失败**，而不是"页面能开但 API 全 500"这种假成功。
- README 前置条件章节经一名不了解本项目的人照着做能起起来（或至少卡点时能立刻知道缺什么）。
- 证据落盘：`docs/fix-program/evidence-93/`。

## 不变项
- 不改产品代码，只改编排与文档。
- 现有 `docker-compose.yml` / `docker-compose.hybrid.yml` 的行为不被破坏（若改动需说明影响面）。

## 前置依赖
- 排在修复队列收官之后（B 组）。
