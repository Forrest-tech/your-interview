## 0. Ground rules for this plan

1. **Every projection credit comes from the re-audit's own estimates** (§5 of the report) or is explicitly labelled as this plan's own conservative estimate with its reasoning shown. No credit is taken twice: where two items touch the same axis, the second takes only the remainder the audit assigned to it.
2. **Verification reuses the re-audit's instruments** — the `TOKENS_JS` census in `reaudit.py` (radii, fonts, colors, shadows, mono count, headings, page widths, middot joins, bare dashes) and the interaction probes in `probes.py` — re-run unchanged against the new build, plus the few new probes each item names. A claim is closed when the probe output says so, not when the code looks right.
3. **The radius scale is amended, openly.** The 票 118 scale declared {6, 10, 14, 999}. The re-audit census shows 8px is the single most common radius in the app (×33 on Dashboard, ×23 on Tracker, ×22 on Playbook detail) because it is the Material button/field radius — it is a de-facto system value, and crushing it to 6px would put every control at war with the component library for no user-visible gain. This plan therefore amends the scale to a **role scale** and enforces it absolutely:

   | Radius | Role |
   |---|---|
   | 6px | Small items: chips, heatmap cells + legend swatches, detail boxes, small fields |
   | 8px | Controls: buttons, inputs, selects (Material geometry) |
   | 10px | Cards, list rows, panels |
   | 14px | Dialogs, drawer, hero panels |
   | 999px | Pills, badges |
   | 50% | Circles: avatars, track nodes/dots |

   Exemptions (Material-internal geometry, enumerated so the census can list them separately instead of silently passing): `mat-form-field` outline corner segments (composite values such as `4px 4px 0px 0px`), scrollbar thumbs, ripple/focus overlays. Any other visible element whose single-value computed `borderRadius` falls outside the role set is a census failure. This amendment, and its reason, must be written into `DESIGN-PLAN.md` §2 as part of R-1 so the next plan inherits one scale, not two.
4. **Copy is trilingual.** The app ships zh/en/fr from `web/src/app/core/i18n/i18n.service.ts`. Every replacement string below is given in all three locales; en is the design language, zh/fr follow the same sentence structure.
5. **No new colors, fonts, or radii are introduced anywhere in this plan** — including by the structural signature in §9, which reuses the shipped stepper's geometry constants verbatim (**16px nodes on a 2px rail**, `tracker.component.scss:287-316`, re-verified in R2; R1's "15px / 2.5px" was invented and is struck wherever it appeared). §C's additions are exactly two kinds, both enumerated where they are specified: motion *duration/easing* tokens (C-1) and wash tokens (C-3 — two brand-alpha values, `--hover-wash` / `--press-wash`, alpha derivatives legal under R-2's whitelist, plus the shell's existing white-alpha hover value tokenized as `--hover-wash-dark` for the midnight bar). No new hues, no new fonts, no new radii. (R2's version of this rule claimed "motion tokens only — no new visual values"; C-3's wash tokens contradicted it. Corrected in R3 — see R2-8 in Appendix C.)
6. **Factual discipline.** Any claim about the current tree in this revision names the file and line it was verified at (Appendix B), and Appendix V records the verifying evidence for every load-bearing claim. Where an earlier revision asserted a fact that verification contradicted, the correction is written into the item itself and logged in Appendix C — never silently swapped.

## R-9 — The structural signature: "The Track" (the audit's ceiling-breaker)

**Audit basis:** the report's honest-ceiling note — items 1–8 are all execution work on tokens and copy, and tokens "top out" at ≈9.2–9.4 because, in the audit's words, the two surfaces it praised (the Tracker stepper, the Tracker flow view) share a visual language that the rest of the app never adopted: everywhere else the product is competent, generic card-and-chip SaaS layout. The audit names the missing move explicitly: extend the pipeline/stepper language into page layout structure. This item is that move, designed concretely.

### The motif

One geometry, already shipped in miniature — the **Tracker list stepper** (`tracker.component.scss:287-316`, all values re-verified in R2):

- **Nodes: 16px circles, 2px border** (`.sp-dot`, `:287-294`). **Rail: 2px** (`.sp-line`, `:310-316`).
- **Reached** — a stage the application has reached, *including the current frontier*: the shipped stepper gives the current stage the same filled treatment as done stages (`[class.done]` covers both; current is distinguished by position and label, not by a different glyph) — **brand border + brand fill + halo `0 0 0 4px rgba(46, 58, 140, 0.14)`** (`.sp-stage.done .sp-dot`, `:305-309`).
- **Future** — white fill, **2px border `#C3C9D4`** (`:293`).
- **Terminal verdict** — on a terminal row, the current node takes **white fill, a verdict-color 2px border, and a 4px verdict halo** (`.term-* .sp-stage.current .sp-dot`, `:297-303`): go `rgba(27, 127, 75, 0.15)` / stop `rgba(179, 38, 30, 0.13)` / attention `rgba(176, 106, 0, 0.15)` / parked (border only, no halo).

The flow view is a sibling rendering of the same stage grammar, not a gradient scale: its Sankey nodes are **flat** — fill `var(--signal-tint)`, stroke `var(--signal-soft)` (`tracker.component.scss:699-700`), links stroked `#C6CDEA` (= `--signal-soft`) at 0.6 opacity. **No multi-step funnel hex scale exists anywhere in the product** — R1's "#C7CDF0 → #2E3A8C funnel scale" was invented, and both R1 mocks hard-coded it; struck here and in the regenerated mocks. ### The geometry contract (what makes it one language, not two new decorations)

The stepper, the band, the rounds track, and the Tracker drawer's communication timeline must share **one** style source: node diameter **16px**, node border **2px**, rail width **2px**, the state treatments and rail colors quoted above, defined once (shared SCSS partial / CSS custom properties) and consumed by all four. Three dialects exist in the tree today, measured in R2: the stepper (16px / 2px, above); the **drawer timeline** — `.tl-dot` is **20px** with a 2px `#D4D9E0` border, its rail is **2px `#E3E6EA`**, and its done glyph is a brand border + 8px brand center dot (`application-detail-dialog.component.ts:712-731`) — and R1's mock invention (struck). The drawer timeline is therefore **migrated** onto the shared constants as part of this item (dot 20px → 16px, rail `#E3E6EA` → the pending rail color, done glyph → the reached treatment); R1 left this conditional on phase-0 measurement, and the measurement is now done — it differs, so the migration is definite scope. ### Why this raises Identity (8.5 → toward 9.5) rather than decorating

1. **The recognition test.** The audit's identity finding is that the app is recognizable only by its topbar. Test: hide the chrome — can you still tell this is Your Interview and not any tracker SaaS? Today, no: cards and chips are universal. After R-9, three of the four main surfaces are *organized by* the track: Dashboard opens with it, Playbook detail is built down it, Tracker rows carry it, the flow view draws its sibling form. The motif is the layout, not an ornament applied to the layout.
2. **It carries information the layout currently doesn't.** The band puts the funnel's shape — counts by stage, the verdict terminus — at page level where today a chips card buries it; the rounds track's fill encodes *how far through this application's process you are* — a fact no current element states (today you open rounds one chip at a time and reconstruct progress yourself). Per the frontend-design skill, structure itself is information; a motif that encodes state passes that test, a repeated logo or color wash would not.
3. **It obeys the skill's restraint rule.** The boldness is spent in exactly one place — the pipeline metaphor, which is the product's actual domain (a job search *is* a pipeline) — and it introduces **zero** new colors, fonts, radii, or iconography. It reduces the number of visual systems in the app from "stepper language + generic cards" to one language at two scales. Tech Stack deliberately gets **no** track: it is a library, not a sequence, and forcing the motif there would be the decoration this item exists to avoid. (Numbering/markers only on true sequences — stages and rounds are true sequences; topics are not.)
4. **It is falsifiable.** If the next audit's screenshot set still reads as generic SaaS with the topbar covered, this item failed and the identity credit in §11 should not be taken. The claim is staked on that test.

### Risks, stated honestly

- **Two dialects risk (the big one).** If the band/track geometry deviates from the stepper's constants by even a couple of pixels, Consistency drops instead of Identity rising — the app would have two similar-but-different track languages. This risk is no longer hypothetical: the tree already holds two dialects (stepper vs drawer timeline, measured above), and R1's mocks invented a third. Mitigation: the single style source above + the geometry probe as a merge gate, not a suggestion.
- **Vertical space on Dashboard.** The band (band + caption ≈ 110px) replaces a half-width card; the Action-center row keeps Upcoming + Weak areas, stats and below are unchanged. Net page-height delta ≈ +0–40px, verified by before/after screenshot diff in implementation. If it exceeds that, the band's padding compresses before anything else moves.
- **Accordion risk on Playbook detail.** Content that was one click (chip) becomes expand-in-place; a user comparing two rounds' prep reports can no longer open both panels side by side — they couldn't before either (the chip selector showed one round at a time), so this is parity, but collapsed-node facts must stay as specified or the change is a net information loss. The expansion motion is specified in C-4.
- **Progress semantics.** Rounds can be skipped or added out of order. Fill rule, pinned: a round counts as "done" for fill purposes iff it has a recorded outcome or its date is past; "current" = the earliest round with a future date and no outcome. Node glyphs on the track are only reached/hollow — a round's verdict is stated in its fact row (Outcome value, in the verdict color), never implied by the node. If the round data model cannot express an outcome for a past round, that round renders filled by date and the fact row shows Outcome "Not recorded" — the track never claims a verdict the data doesn't hold.
- **Narrow viewports.** Under 900px the band keeps node geometry, stage labels are the Tracker's own one-word status names (the `status.*` i18n keys behind `statusLabel`, `tracker.component.ts:1336` — the product has no separate short-name set, and R1/R2's "the short names the Tracker already uses" implied one; corrected in R3), and counts stay — the band never wraps into two rows (a wrapped track is a broken metaphor).
