# 票 94 — 网关 /health/live 在部分起服务的环境里恒 503:聚合健康与真实可用性脱节

严重度：S3（不是功能缺陷，但会让编排与自检**误判**，进而引发假的"起环境失败"）
来源：A2 E2E 套件健康检查时实测发现（2026-10-23 沙盒内）

## ⚠️ 本票结论的更正（2026-10-23 晚，读 docker-compose.yml 后自行推翻初判）

初判写的是"ocr 服务在多数环境里并不存在" —— **这个前提错了**，如实更正：

- OCR 服务**是存在的**：`docker-compose.yml` 里有 `ocr-service`（容器名
  `yourinterview-ocr`，票 59 落地，PaddleOCR PP-OCRv6，**本地**识别，端口 5300）。
  它不是云 API，不需要外部凭据。
- 我实测到的 503，直接原因是我当时**手工起服务**（逐个 `dotnet run` 起 7 个业务服务）
  时**没有起 OCR 服务**，于是网关探活 `ocr → 127.0.0.1:5300` 必然失败。
- 也就是说：**这是一次"我自己没起全"造成的 503，不是配置缺陷**。
  在完整 `docker compose up` 下，ocr-service 会起在 5300，探活不会失败。

## 那么本票还成立吗 —— 成立，但性质变了

成立的理由不是"OCR 不存在"，而是：

1. **部分起服务的开发场景是常态**（本地调试只起 identity + 某几个服务）。
   网关 Program.cs:31-42 的注释**早已记载过这个坑**：
   "探活必然失败 ⇒ 整体 Unhealthy ⇒ /health/live 恒返 503 …… 网关自己其实完全健康，
   调用链也没问题，但任何依赖 /health/live 的东西都会误判它没起来"。
   并且它**已经预留了解法** `ReverseProxy:HealthChecks:EnabledClusters`，
   但**从未配过**，于是旧行为（全探）持续生效。
2. **OCR 服务很重**（PaddleOCR，compose 里给它 120s start_period + 20 次重试）。
   让它参与"网关是否可用"的判定并不合理 —— 网关转发业务 API 并不依赖 OCR，
   OCR 挂了不该让网关整体报不健康。
3. 我已经实测了两件互相矛盾的事实，说明旗标确实撒谎：
   - 逐个探 5262–5268：`/health/live` **全部 200**
   - 网关聚合 `/health/live`：**503**
   - 而 `POST /api/auth/login`：**200**（API 完全可用）

## 任务
- 配置 `ReverseProxy:HealthChecks:EnabledClusters`，显式列出要探的集群：
  `identity,jobs,interviews,knowledge,assessment,analytics,aigateway`。
  **OCR 排除在健康探活之外**（网关转发业务 API 不依赖它；OCR 自身的可用性由票 92
  的金标准回归集去守，那才是它该被度量的地方）。
- 不改探活路径口径（仍为各服务的 /health/live），不引入第二套健康判定。

## 验收
- **正向**：起 7 个业务服务 + 网关（**不起** ocr）→ 网关 `/health/live` 返回 **200**。
- **反向（必须做）**：故意停掉 7 个中的任意一个（如 knowledge 5265）→ `/health/live`
  必须返回 **503**。只验"变绿"不算验收 —— 必须证明它**还能探出真故障**，
  否则就是把旗标改成永远说好话，那更糟。
- E2E 健康检查（e2e/health.setup.ts）改回用 /health/live 后仍能正常放行。
- 证据落盘：`docs/fix-program/evidence-94/`（三次状态：全起 / 停一个业务服务 / 停 OCR）。

## 相关票
- **票 92**（OCR 入口接全）：OCR 可用性的度量归它（金标准回归集），本票只管不让它
  拖垮网关健康判定。
- **票 93**（B4 一条命令起环境）：本票是它的前置，自检报告要靠这个旗标准 ——
  否则"哪个服务没活一眼可见"会变成"OCR 没起 → 报告说网关挂了"，指错方向。
- **票 88**（CI）：CI 里若用网关 health 做依赖等待，同样会被它卡住。

## 记一笔教训
初判时我只看了 appsettings 里"OCR 集群指向 5300 且那端口没东西"，就写了
"OCR 服务不存在"。**没去 docker-compose.yml 确认那个端口到底该由谁提供**，
就下了一个关于"服务是否存在"的结论。结论错了要自己推翻，不要让它留在票面上
误导后面接手的人 —— 尤其在 B4 正要靠这套 compose 做自检的时候。
